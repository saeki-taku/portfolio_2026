## 5. 実装順序と完了条件

順番はユーザー指定。後段を先に完成させるために飛ばさない。既存の実装済み部分は確認して再利用する。

### 1：Astro＋Workersの土台

- 通常ページを事前生成し、静的配信と必要なAPI処理をWorkersにまとめる。
- 現在の土台を読み、check/buildとローカルWorkersの疎通を確認する。フレームワークを入れ替えない。
- Pages分割・Next.jsへの移行は行わない。

### 2：凛のPC/SP固定構図

- 最新採用素材へ合わせ、PC/SPでそれぞれの構図・人物・色調を確認。
- 通常表示ではトップの縦横スクロールなし。絵の縦横比を歪めず、無理な拡大で人物や窓を切らない。
- ロゴと実績・お知らせ・問い合わせへの導線を表示。内容は下層へ。
- 画面下部にお知らせ1件を置く案は未決定。勝手に追加しない。
- 小画面・横向き・タブレットも確認。拡大表示や文字拡大時は情報・操作を切り捨てない設計を選ぶ。

### 3：天気・季節、その後に髪・手

- 日本時間（Asia/Tokyo）と実天気に連動する。
- 閲覧者の国内地域をIP由来情報で推定し、手動変更可能。取得不可・海外は東京。凛・縁・卓で地域は共通。
- IP推定は正確な現在地ではない。位置情報許可を求めるGPS方式へ勝手に変更しない。
- 地域別カレンダーを基本に観測情報で季節を補正。桜はつぼみ→開花→満開→散り際→葉桜など段階管理。当日の気温だけで逆戻りさせない。
- 地域の日の出・日没と時刻で昼夜を判断する。取得失敗・遅延・未知値・古い値への代替表示を設計する。
- 昼は人物あり。夜在室は人物と暖かい室内灯。就寝は人物なし・消灯。晴れは微かな月明かり、曇雨はさらに暗い。太陽・月は原則光で表す。
- 雨に強い日差しを残さない。閉窓の室内や人物の上へ雨・花びらを重ねない。
- 画像＋CSS＋Canvas 2Dから必要性を判断する。PixiJS/WebGL/Three.jsは未採用。
- 人物・背景・影・動く部位を分け、隠れていた箇所を補完する。服や紙まで歪ませる一枚絵のUV変形を完成扱いしない。
- 閉窓の髪を外風へ直結しない。動きは小さく、休止を含める。prefers-reduced-motion、一時停止、非表示タブでの停止、静止画の代替を用意。
- APIサービス・初回の季節/天候範囲・公開する手動天気UI・具体的な動作は候補を示して相談する。秘密鍵が未設定なら明示したローカルfixtureで検証し、実API接続済みと称さない。

### 4：実績・お知らせのMarkdown管理

- Astro Content Collectionsで実績とお知らせを分ける。Codex等への依頼でMarkdownと画像を更新し、再ビルドして反映。
- 実績ごとに画像と説明の詳細ページ。共通項目・共通レイアウトを使用。
- CMSは初期導入しない。実績の内容・成果・日付を作り話で埋めない。
- 一覧/詳細/下書きの扱いと必須項目を決め、リンク・日付・画像を検証する。

### 5：D1・管理画面・CSV・通知と自動返信

- 名前・メールアドレス・相談内容を受け付け、サーバー検証後にD1へ保存する。
- 管理者通知と送信者への受付メール。保存とメール送信の状態を区別し、再送と二重送信防止を設計する。
- 本人だけがアクセスできる問い合わせ一覧とCSV出力。画面だけでなくAPI・CSV経路も認証する。
- 日本語、改行、カンマ、引用符を含むCSVを検証。表計算ソフトの数式として実行され得る値を安全に出力する。
- 認証方式、メールサービス（Resendは候補）、ドメイン、迷惑送信対策、保存期間は未決定。必要時に相談する。
- 実個人情報をリポジトリ・スクリーンショット・公開ログへ残さない。試験はダミーデータ、ローカルDB、メールのモックを基本にする。
- 無料枠を想定するが無制限としない。料金は実際の採用時に公式資料で再確認する。

1. 同じ作業ディレクトリを同時に編集しない。それぞれ専用worktree・別ブランチを使う。
2. 開始時に作業ディレクトリ、branch、HEAD、未コミット差分、他方の担当を確認する。元の試作と実装worktreeは読み取り参照にする。

4. 担当は「段階・変更対象ファイル・公開インターフェース・完了条件」で区切る。担当が未指定なら既存実装の読み取りと作業案まで進め、編集前に担当を確認する。
5. 例：段階2では一方が画像表示/CSSを実装し、もう一方は読み取りレビューと受入確認。段階3では一方が地域・時間・天気の状態計算、もう一方が定義済み状態を描画する処理。これは分担案であり、自動割り当てではない。
6. `package.json`・lockfile・Astro/Workers設定・共有CSS・トップページ・DBスキーマなど共通ファイルの変更担当は一人にする。必要変更は他方に提案し、両方で同時に更新しない。
7. 同一段階内の独立作業を並行する。段階4/5を先行させない。統合時は承認済みのコミット単位でレビューし、統合担当がmerge/cherry-pick後に検証する。
8. 他方の未コミット変更を上書き・reset・clean・stash・一括コミットしない。衝突箇所だけ切り分け、独立作業を続ける。
9. 開発サーバーは異なるポート。既存記録は開発4398・preview4399。実際の使用状況を調べ、他方のプロセスを停止しない。
